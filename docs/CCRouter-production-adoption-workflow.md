# CCRouter 生产项目场景驱动演进流程

## 1. 目的

生产项目是验证 CCRouter 能力、边界和稳定性的主要依据，但单个项目的业务特例不能直接
转化为框架公开 API。每个真实场景都必须先确认现有能力、应用与框架职责、失败语义和通用性，
再决定使用、修复、增强或暂缓。

本流程适用于：

- 在生产功能开发中判断 CCRouter 是否已经支持某个场景；
- 发现现有 API 难用、语义不完整或行为错误；
- 评估是否应新增 Route、Service、Command、Event、InitTask、Scope、诊断或生成器能力；
- 使用真实业务规模验证性能、并发、生命周期和生成物正确性。

## 2. 基本原则

1. 先证明问题，再修改框架；不能仅因为“可以实现”就增加公开 API。
2. 先使用现有最窄能力；不要用新的万能接口绕过 Route、Service、Command、Event 或 InitTask。
3. 区分框架缺陷、接入错误、文档缺口、应用职责和新的通用能力。
4. 生产业务数据只能用于验证行为，不进入框架日志、测试夹具或提交历史。
5. 改动应可回退、可对比；共享 API 变更优先通过独立路径或明确开关验证。
6. 每个结论都需要代码、测试、诊断记录或可复现步骤支持，不能依赖主观推断。

## 3. 场景输入

开始评估前至少记录：

- 业务目标、用户流程和触发入口；
- Host、组件、调用方和目标组件；
- 是否涉及跨组件 Contract、Deep Link、第三方 Navigator 或平台入口；
- 输入、输出、失败、取消、超时和降级要求；
- Owner、Scope、创建和销毁时机；
- 并发量、性能目标、隐私与安全边界；
- 当前实现、期望结果、实际结果和稳定复现步骤。

缺少这些信息时可以先做只读排查，但不能提前设计公开 API。

## 4. 能力映射与分类

先映射到现有 Route、Service、Command、Event、InitTask、Interceptor、PopGuard、Aspect、
Analytics、Scope、Host/Outlet、Adapter 或 Generator。随后只能归入以下一种主分类：

### A. 已支持

现有稳定 API 能完整表达场景。只补生产接入、测试或示例，不修改框架契约。

### B. 框架缺陷

现有承诺与实际行为不一致，或存在类型、生命周期、并发、资源释放、诊断、性能或安全错误。
先增加失败回归，再做最小兼容修复。

### C. 开发体验或文档缺口

能力存在，但命名、生成物、错误提示、文档、Demo 或诊断不足。优先改进工具和指导，不新增
重复业务 API。

### D. 应用层职责

业务规则、状态管理、网络协议、供应商 SDK 配置、隐私决定或页面局部 UI 不应进入 Core。
框架最多提供稳定契约或 Adapter 边界。

### E. 新的通用框架能力

现有模型无法保持场景语义，并且能力能服务多个组件或项目。必须先完成 API、Owner、生命周期、
错误、并发、降级、诊断、性能和兼容性设计，再决定版本范围。

### F. 条件触发或暂缓

收益尚未达到复杂度成本，或依赖平台能力、规模数据和稳定 Entry/Contract。记录触发条件和证据，
不发布占位 API，也不使用语义较弱的拼接实现冒充支持。

## 5. 候选方案评估

非简单接入场景至少比较以下方案：

1. 使用现有框架能力；
2. 仅在应用或组件内部实现；
3. 增加可选 Adapter、生成器或工具能力；
4. 修改 Core 契约；
5. 暂缓并增加诊断观测。

每个方案必须说明收益、缺点、实现成本、迁移成本、兼容风险和回退方式。推荐方案应优先满足
最小公开表面积、编译期校验、明确生命周期、可测试、可诊断、并发安全及性能稳定。

## 6. 实施顺序

1. 建立可复现用例，并用现有诊断确认问题边界。
2. 增加失败、生命周期、并发或性能基线测试。
3. 更新对应设计文档，标明支持范围和明确不支持项。
4. 实现最小闭环；内部能力保持私有，业务只使用稳定 Facade 和生成契约。
5. 在 Demo 建立无业务数据的通用示例。
6. 在生产场景验证成功、失败、取消、超时、降级和资源释放。
7. 执行 Analyze、专项测试、全量回归和适用的 `generate --check`。
8. 更新 README、集成 Skill、API 注释和任务状态，单独提交。

生产接入与框架修改应尽量拆成可独立审查的提交。框架修复不能依赖生产项目的私有源码才能
测试，生产项目也不能通过导入 `src`、Runtime 或 Adapter 内部实现临时绕过边界。

## 7. 新公开 API 门槛

新增公开声明前必须能回答：

- 真实使用者是谁，为什么现有能力无法表达；
- 它属于业务 API、组件作者 API、Host/Adapter SPI 还是测试 API；
- 谁创建、拥有、关闭和销毁；
- 同步、异步、取消、超时和重入语义是什么；
- 能力不足时如何明确失败或安全降级；
- 会记录哪些安全诊断，禁止记录哪些业务数据；
- 是否能在 Pure Dart 或隔离 Flutter 测试中确定性验证；
- 对启动、热路径、内存、生成速度和兼容性的影响；
- 如何灰度、A/B 对比或回退。

任一关键问题没有答案时，保持内部实现或归入条件触发计划。

## 9. 完成标准

一个生产场景只有在以下条件满足后才算处理完成：

- 已明确是使用、缺陷、体验、应用职责、新能力还是暂缓；
- 没有通过内部 API、任意 Map、反射或静默降级绕过框架契约；
- 相关行为具有自动化测试或明确的平台验证记录；
- 生命周期、错误、诊断、性能和隐私边界与实现一致；
- 文档、Skill、Demo 和任务状态没有把计划能力描述为已实现；
- 生产接入可以回退，框架改动可以独立验证。
